# 串口诊断与小智方案

双击「交互终端展示」，或在项目根目录运行 `python .\tools\serial_monitor.py`。默认 COM18、921600，Ctrl+C 退出。日志自动追加到 `logs/serial/日期-COM18.log`，包含转写，不保存原始音频。用 `--no-log` 只看不存，`--log 路径` 自定义文件，`--replay 路径` 回放。烧录前先退出工具，释放串口。

| 看到的最后阶段 | 目前能够判断什么 |
|---|---|
| 没有收音开始 | 没看到云端检测到说话；仍需区分麦克风、网络、服务端 VAD |
| 收音结束，无转写 | 板端还没收到转写事件 |
| 转写正确，计时已执行 | 板端动作成功；喇叭是否播出来另看音频链 |
| 首段回复音频到达 | 音频已到板上；这条日志早于 I²S 写入，不能证明扬声器发声 |
| 首段音频前断线 | 先查 WebSocket 关闭原因、帧长与网络；不能仅凭静音认定功放故障 |

已复现的「你好」无声：转写成功后，板端收到 25,800 字节的 WebSocket 帧，超过原 15,360 字节上限，主动发关闭码 1009。对应日志是 `ALI_WS_FRAME_REJECT` 和 `ALI_WS_LOCAL_CLOSE`。构建脚本将 ESP32 接收上限调到 64 KiB，超过原上限的帧缓冲分配到 PSRAM，保留关闭诊断。

优先借鉴小智固件的[音频任务和队列](https://github.com/78/xiaozhi-esp32/blob/main/main/audio/README.md)：网络收包、解码和 I²S 播放分开。本项目当前在 WebSocket 回调里直接等待 audioLock 和写 I²S。下一步先记录 WebSocket 关闭码、帧长、首段音频和 I²S 写入结果；如果帧已到达且播放堵塞，再换成有界 PCM 队列和独立播放任务。首帧前断线需要另查，改队列无法补回未收到的首帧。

小智后端的[接收处理](https://github.com/xinnan-tech/xiaozhi-esp32-server/blob/main/main/xiaozhi-server/core/handle/receiveAudioHandle.py)将语音检测和 ASR 分开，[发音频处理](https://github.com/xinnan-tech/xiaozhi-esp32-server/blob/main/main/xiaozhi-server/core/handle/sendAudioHandle.py)独立控制发送节奏。值得借鉴的是阶段日志和分段测时，可参考其[性能测试工具](https://github.com/xinnan-tech/xiaozhi-esp32-server/blob/main/main/xiaozhi-server/performance_tester.py)。整套迁移需要常驻服务，并且小智的二进制 Opus 协议与当前百炼的 JSON/PCM 不可直接互换。现阶段保留板端直连和已验证的本地计时校验。
